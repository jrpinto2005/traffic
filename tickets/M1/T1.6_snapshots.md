# T1.6 — Initial-state snapshots

**Archetype:** Builder · **Depends on:** T1.4 · **Implements:** `D-032`, `D-018`

## Context
Per `D-032`, warm-up from empty is *how a snapshot is produced*; a snapshot is *how warm-up
is avoided* on every later run. Warming up once per (network, demand level, seed) and reusing
the state removes warm-up wall-clock from the overwhelming majority of runs in a sweep.

## Contract

```python
class WarmupDesign(StrEnum):
    SELF = "self"                        # each arm warms up under its own controller
    NEUTRAL_SNAPSHOT = "neutral_snapshot" # all arms load one Webster-generated state

def snapshot_key(net_hash: str, demand_level: float, seed: int, design: WarmupDesign) -> str
def produce(...) -> Path      # run warm-up, save state, record network hash + SUMO version
def load_into(backend: Backend, path: Path) -> None   # hard error on hash mismatch
```

**Self warm-up is the default.** It answers "what steady state does each controller induce",
which is the M1–M5 question. Neutral snapshots answer "given this state, who recovers best"
and are for shock experiments.

**Rule:** whichever design an experiment uses, it is the **same across all arms** and it is
recorded in the manifest. Mixing them within one comparison invalidates it.

## Scope
1. Snapshot production, caching by key, and loading.
2. Network-hash and SUMO-version guards; mismatch is a hard error, never undefined behaviour.
3. Both warm-up designs.
4. Manifest field `warmup_design`.

## Non-goals
1. Do NOT decide warm-up *length*. That is T1.8 (MSER-5).
2. Do NOT implement MPC's estimate-initialised prediction. `D-032` notes M6 inherits this
   facility; M6 builds on it.
3. Do NOT invalidate the cache on unrelated config changes — key on the four fields only.

## Acceptance criteria
- [ ] A produced snapshot loads and yields the identical `TrueState` it was saved from.
- [ ] Loading against a different network fails with a clear error.
- [ ] Loading under a different SUMO version fails with a clear error.
- [ ] Two arms under `NEUTRAL_SNAPSHOT` with the same seed start from identical state.
- [ ] `warmup_design` appears in the manifest for every run.

## Escalate if
1. SUMO state files do not round-trip exactly.
2. Snapshot behaviour differs between TraCI and LibSUMO.

## Note for the builder, 2026-10-07 — measured during T1.14

**Right after `loadState`, SUMO reports an empty pending-vehicle list**, although the insertion
backlog itself is restored: one step later the count matches a continuation that was never
snapshotted. Measured on 1.27.1, both transports. `RunCounters.insertion_failures` is that
pending count (T1.4's audit), so the `TrueState` projected at the instant of a load
under-reports insertion loss by the whole backlog. A snapshot policy must not read validity
counters at the load step; `tests/backend/test_counters_and_snapshots.py` documents the case.
