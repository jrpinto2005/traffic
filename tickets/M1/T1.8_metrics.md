# T1.8 — Metrics, validity checks, and run phases

**Archetype:** Builder · **Depends on:** T1.2, T1.4, T0.4, T0.5
**Implements:** `D-006`, `D-008`, `D-018`, `D-022`, `D-025`

## Context
Correctness-critical. Per `02_PROJECT_CHARTER.md` §8 methodology carries the highest quality
bar in the project, because a mistake here is **retroactive**: it does not produce a bad
controller, it produces a folder of results that were never valid.

## Contract
Implement exactly the definitions in `07_EXPERIMENT_METHODOLOGY.md` §2. That document **is**
the contract. Primary delay is **time loss** (`D-006`); a queue is **halting below 0.1 m/s
continuously for ≥ 1 s, counted in vehicles** (`D-025`).

```python
class MetricAccumulator:
    def accumulate(self, state: TrueState) -> None:   # every step; array appends only
    def finalize(self) -> MetricResult:               # at window close; NumPy

class RunPhase(StrEnum):
    WARMUP = "warmup"; MEASUREMENT = "measurement"; COOLDOWN = "cooldown"
```

**Every vehicle-level and network-level metric is computed per vehicle type as well as in
aggregate**, from M1, before motorcycles exist (`07_EXPERIMENT_METHODOLOGY.md` §2.4).
Retrofitting separability after the aggregation code is written is far more annoying than
building it in.

**Validity gate** (`D-008`): a run is invalid — not merely noisy — on any teleport, on
insertion failures above threshold, on detected gridlock, or on a snapshot hash mismatch.

**Insertion loss is the check that will actually fire at M1**, and it needs a justified
threshold rather than a placeholder. T0.4's corrected sweep produced **zero teleports** at every
demand level on an isolated intersection while 22% of configured demand failed to enter, and
mean time loss rose only from 21.7 s to 60.0 s — because the vehicles that would have suffered
worst never departed. That is a plausible-looking result over 78% of the intended demand.
Teleporting becomes the dominant threat at M5, where a vehicle can be trapped between signals
instead of spilling out of the network.
Invalid runs are **written with their flag, never dropped**: a missing run and an invalid run
are different facts, and silently dropping invalid runs biases the comparison toward whichever
controller gridlocks less.

**Trip accounting** (`D-022`, `07_EXPERIMENT_METHODOLOGY.md` §4): three separate counts —
boundary sink, mid-link arrival, still in-network. The first two are served; the third is not.
The **trip completion rate accompanies every travel-time metric**, because travel-time means
cover completed trips only, and a controller that queues indefinitely has its slowest vehicles
excluded from its own average.

## Scope
1. All metrics of `07_EXPERIMENT_METHODOLOGY.md` §2, with per-type separation.
2. Three-phase run structure; metrics collected in MEASUREMENT only.
3. MSER-5 warm-up truncation, plus a running-average series for the visual confirmation §3.2
   requires.
4. Validity gate and invalidity flags. **You own invariants 13–14** of
   `05_DOMAIN_MODEL.md` §8: `teleports == 0` for any valid run, and
   `arrived_at_sink + arrived_mid_link + still_in_network == total inserted`.
5. Three-way trip accounting.
6. Accumulate into arrays during the run; compute with NumPy at window close (`D-031`).

## Non-goals
1. Do NOT compute confidence intervals or run comparisons. That is T1.12.
2. Do NOT add emissions or fuel metrics. Out of scope, `02_PROJECT_CHARTER.md` §7.2.
3. Do NOT allow any validity check to be disabled by configuration. `D-008`.
4. Do NOT compute metrics per-vehicle in Python inside the step loop. `D-031` hot path.
5. Do NOT invent a metric not in §2. If you think one is needed, escalate.

## Acceptance criteria
- [ ] Time loss computed by us matches SUMO's `timeLoss` within floating-point tolerance.
- [ ] Queue count matches a hand-computed value on a fixture with known halting durations,
      including a vehicle halting for 0.5 s that must **not** count.
- [ ] MSER-5 selects a sensible truncation point on a synthetic series with a known transient.
- [ ] A run with an induced teleport is flagged invalid and still written.
- [ ] Trip accounting sums to total inserted (invariant 14 of `05_DOMAIN_MODEL.md` §8).
- [ ] Every metric has a per-vehicle-type variant, tested with two types.
- [ ] Profiling: accumulation adds less than a stated fraction of step time; report it.

## Escalate if
1. T0.5 found SUMO's halting counters differ from `D-025`'s assumption and the decision was
   not amended.
2. MSER-5 gives unstable truncation points across seeds — that is a methodology finding.
3. Any metric in §2 cannot be computed from `TrueState` as projected by T1.4.

## Definition of Done
`08_AGENT_HANDOFF_PROTOCOL.md` §5, Builder. Include the profiling number.

### A1. Two sources (`D-035`)
- **Trip level, from tripinfo, at run end.** Add `traffic_lab/domain/trip.py` with a frozen,
  slotted `TripRecord` (vehicle type; scheduled and actual departure; insertion delay; arrival
  or `None`; travel time or `None`; time loss; waiting time; stops; departure and arrival
  `LaneId`; exit `SINK` / `MID_LINK` / `None`), and `traffic_lab/backend/tripinfo.py` with

- **Step level, from `TrueState`, every step:** queue per lane, max queue, and the time loss
  accumulated by vehicles still in-network when the window closes.

### A2. Definitions pinned
- **Delay** (`D-006` as amended) = `timeLoss + departDelay`, always reported with both parts.
- **Completed in the window** = arrival time in [window start, window end). Mean delay,
  travel time, waiting time, stops, approach delay (by departure lane's approach) and
  throughput are over these trips; completion rate = completed / (completed + in-network at
  window end).
- **Stops** = tripinfo `waitingCount`, and **waiting time** = tripinfo `waitingTime`, **if** a
  real run shows they match `07_EXPERIMENT_METHODOLOGY.md` §2.1 (in particular: is an insertion
  at standstill counted as a stop?). If not, escalate.
- **Sink vs mid-link** from the trip's arrival position against its arrival lane's length;
  verify on a scenario with declared `arrivalPos` (mid-link) and without (sink).
- **Signal utilisation is out of scope** (needs T1.5 and T1.14).

### A3. Validity gate (`D-008`, `05_DOMAIN_MODEL.md` §8 invariants 13–14)
- Invalid on: any teleport; **insertion loss > 1 %**; gridlock; snapshot mismatch. Not
  configurable. Invalid runs are written with their flags, never dropped.
- **Insertion loss** = `RunCounters.insertion_failures` (SUMO's pending list, T1.4) at the step
  the measurement window closes, divided by the number of trips whose *scheduled* departure
  falls in the window (from tripinfo). If undeparted records do not carry a usable scheduled
  time, escalate.
- **Invariant 14:** at run end, completed + still-in-network from `RunCounters` must equal the
  inserted trips in tripinfo **exactly**; a mismatch is a defect in our accounting and
  **raises**, it is not a property of the run. The sink/mid-link *split* from tripinfo is
  authoritative; where it differs from `RunCounters`' kinematic split, report the count.

### A4. MSER-5
Generic over a 1-D series. Feed it per-trip delay ordered by arrival time, the primary
metric's series (`07_EXPERIMENT_METHODOLOGY.md` §3.2); report the truncation as a simulated
time, plus the running-average series for the visual check.

### Rulings on the builder's escalations, 2026-10-07 — binding
The builder verified tripinfo against real SUMO before coding and stopped on three points, each
with evidence. Ruled by the architect:

- **E1 — stops.** SUMO's `waitingCount` counts an insertion at standstill as a stop when the
  vehicle is still halted at its first move step, and nothing can separate that case. Stops =
  `waitingCount`; `07_EXPERIMENT_METHODOLOGY.md` §2.1 amended to say so, together with
  `waitingTime`'s convention (insertion step excluded, unlike `timeLoss`).
- **E2 — scheduled departure of undeparted trips.** For those records `departDelay` is
  measured to the instant the file was written, which the file does not record. Signature is
  now `read_trips(path, index, *, end_s)`; the caller passes the simulated time at close, and
  scheduled departure = `end_s − departDelay` (departed trips: `depart − departDelay`).
- **E3 — vehicle type.** Tripinfo carries the SUMO type ID, not the class. `BackendIndex`
  gains `vehicle_types: Mapping[str, VehicleType]`, the map `start()` already builds for the
  projector — one source of truth. The "do not touch `adapter.py`" line is lifted for exactly
  this change. A trip whose type is not in the map raises.
